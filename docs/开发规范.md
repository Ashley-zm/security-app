# 安检 APP 开发规范

> 适用项目：`cyc-security-app`
> 技术栈：uni-app（Vue 3 + `<script setup>`）+ TypeScript + Pinia + Vite + SCSS
> 编译目标：H5、App-plus（Android 原生插件 AI 检测）

本规范从当前代码库已落地的约定中提炼而来，**以代码现状为准**。新增或修改代码时请优先复用既有模式，避免引入第二套风格。

---

| 维度 | 选型 |
| --- | --- |
| 框架 | uni-app `@dcloudio/uni-app` 3.x |

## 2. 目录结构与分层

```
api/        接口请求模块（按业务域拆分，函数以 Api 结尾）
components/ 全局通用组件（PascalCase，通用组件加 App 前缀）
pages/      页面，每个页面一个目录 + index.vue
stores/     Pinia 状态仓库
types/      TS 类型定义（按业务域拆分）
utils/      工具函数（request / storage / permission / validate ...）
styles/     SCSS：variables / mixins / common
static/     静态资源（图片、tabbar 图标）
nativeplugins/ uni-app 原生插件（Android AAR）
```

**分层职责边界（不得越层）：**

- 页面（`pages`）只编排 UI 与交互，业务数据走 `stores` 或 `api`，不直接写 `uni.request`。
- `api` 只负责声明接口、组装参数、复用 `request`，不写 UI 逻辑。
- `stores` 负责状态与异步编排，调用 `api`，不直接操作 DOM/页面跳转以外的 UI。
- `utils` 为纯工具，不依赖具体业务。
- 类型集中在 `types`，跨层共享；组件/页面内部私有类型可就近定义（如 `pages/plugin-check/index.vue` 中的 `DetectCallbackResult`）。

## 4. TypeScript 规范

- 全局开启 `strict`，禁止隐式 `any`；确需逃逸时显式标注（如插件回调里的 `globalThis as { plus?: any }`），并尽量收敛在最小范围。
- 路径别名统一使用 `@/`，对应项目根目录（见 `tsconfig.json` 与 `vite.config.ts`）。

  ```ts
  import { request } from '@/utils/request'
  import type { LoginParams } from '@/types/auth'
  ```

- **类型导入用 `import type`**，与值导入区分，避免被打包进运行时。
- 函数/接口的请求与响应都要带泛型，保持端到端类型安全：

  ```ts
  export function loginApi(data: LoginParams) {
    return request<LoginResult, LoginParams>({
      url: '/api/auth/login',
      method: 'POST',
      data
    })
  }
  ```

- 业务类型集中放在 `types/<域>.ts`，按职责拆分 `Form` / `Params` / `Result` / 实体（参考 `types/auth.ts`）。

## 5. Vue 组件规范

统一采用 `<script setup lang="ts">` + 组合式 API。

- **Props / Emits 用类型声明**，带默认值用 `withDefaults`：

  ```ts
  const props = withDefaults(
    defineProps<{ title: string; showBack?: boolean; rightIcon?: string }>(),
    { showBack: false, rightIcon: '' }
  )
  defineEmits<{ rightClick: [] }>()
  ```

- `<script setup>` 内组织顺序建议：导入 → store/props/emits → 响应式状态（`ref`/`reactive`）→ `computed` → 生命周期 → 方法。
- 模板只用 uni-app 内置组件：`view` / `text` / `input` / `button` / `image` / `scroll-view`，**不要用 `div`、`span`**。
- `easycom` 已开启自动扫描（`pages.json`），`components/` 下组件可在模板直接使用，但页面中显式 `import` 也被保留（如 `AppNavbar`），保持与所在文件一致即可。
- 表单状态用 `reactive` 承载对象、`ref` 承载单值；提交类操作要有 `submitting`/`loading` 防重入（参考 `pages/login/index.vue`）。

## 6. 样式规范

- **尺寸统一用 `rpx`**（颜色透明度、阴影 px 等非布局值除外）。
- 颜色、圆角、阴影统一取 `styles/variables.scss` 中的 token，禁止散落硬编码主色：

  ```scss
  $primary-color: #1677ff;
  $text-main: #0b1f44;
  $bg-page: #f5f8ff;
  $card-radius: 24rpx;
  $shadow-card: 0 12rpx 32rpx rgba(28, 83, 171, 0.08);
  ```

- 复用布局用 `styles/mixins.scss`（`app-card` / `flex-center` / `text-ellipsis`），通用类用 `styles/common.scss`（`.page` / `.safe-page` / `.primary-btn` 等）。
- 每个页面/组件的 `<style scoped lang="scss">` 顶部按需 `@import` variables 与 mixins：

  ```scss
  <style scoped lang="scss">
  @import '@/styles/variables.scss';
  @import '@/styles/mixins.scss';
  </style>
  ```

- 底部安全区用 `.safe-page` 或 `env(safe-area-inset-bottom)`；窄屏适配用 `@media (max-width: 420px)`（参考 `plugin-check/index.vue`）。

## 7. 网络请求与 API 层
所有请求统一走 `utils/request.ts` 的 `request<T, D>`，**禁止页面/组件直接调用 `uni.request`**。

### 7.1 请求配置说明

- `api/<域>.ts` 只声明业务接口，调用 `request` 时只传 `url`、`method`、`data`。
- `baseUrl`、`useMock`、`header` 等运行时配置统一维护在 `utils/request.ts`，业务接口文件不单独传这些配置。
- 默认配置使用 `DEFAULT_REQUEST_CONFIG`：当前默认 `baseUrl` 为空、`useMock` 为 `true`，请求头自动注入 `Authorization: Bearer <token>`。
- 单接口特殊配置使用 `ROUTE_REQUEST_CONFIGS`：例如 `/auth/tenant/list` 需要请求真实租户服务，因此在这里配置 `baseUrl: 'http://192.168.99.180:58085'` 和 `useMock: false`。

### 7.2 响应结构说明

请求层统一判断 `code === 0 || code === 200` 为成功，并兼容 `message` 与 `msg` 两种提示字段。

普通详情/操作类接口优先读取 `data`：

```ts
{
  code: 200,
  msg: '操作成功',
  data: {
    id: '1'
  }
}
```

分页列表类接口兼容 `rows + total` 结构，请求层会自动转换为 `{ list, total }`，业务层继续读取 `result.list` 和 `result.total`：

```ts
// 后端原始返回
{
  code: 200,
  msg: '查询成功',
  rows: [],
  total: 6
}

// request 归一化后的业务结果
{
  list: [],
  total: 6
}
```

### 7.3 接口类型说明

- 请求参数类型命名为 `XxxParams`，表单状态类型命名为 `XxxForm`，响应结果类型命名为 `XxxResult`。
- 列表、详情等实体结构单独定义实体类型，例如 `TenantInfo`、`WorkOrder`。
- 每个接口都要显式传入响应泛型；有请求体时同时传入请求泛型。

```ts
export function loginApi(data: LoginParams) {
  return request<LoginResult, LoginParams>({
    url: '/api/auth/login',
    method: 'POST',
    data
  })
}
```

### 7.4 现有接口清单

| 模块 | 接口函数 | 方法 | URL | 中文说明 |
| --- | --- | --- | --- | --- |
| 认证 | `loginApi` | `POST` | `/api/auth/login` | 账号密码登录，提交手机号、密码和可选租户 `tenantId`，成功后返回 token 与用户信息。 |
| 认证 | `changePasswordApi` | `POST` | `/api/auth/change-password` | 修改当前登录用户密码，提交旧密码与新密码。 |
| 认证 | `getTenantListApi` | `GET` | `/auth/tenant/list` | 获取可选租户列表；该接口走真实服务 `http://192.168.99.180:58085`，不走 mock。 |
| 工单 | `getWorkOrderListApi` | `GET` | `/api/work-orders` | 获取工单列表，支持分页、状态和关键字查询；后端可返回 `rows + total`。 |
| 工单 | `updateAppointmentTimeApi` | `POST` | `/api/work-orders/{id}/appointment-time` | 修改指定工单的预约时间。 |
| 首页 | `getHomeOverviewApi` | `GET` | `/api/home/overview` | 获取首页概览数据，如待处理数量、完成数量、预警数量等。 |
| 消息 | `getUnreadMessageCountApi` | `GET` | `/api/message/unread-count` | 获取未读消息数量。 |
| AI 助手 | `askAssistantApi` | `POST` | `/api/assistant/ask` | 向安检助手提交问题，返回回答、检查清单、建议问题和参考资料。 |

### 7.5 新增接口流程

1. 在 `types/<域>.ts` 定义 `Params` / `Result` / 实体类型，并为关键字段补充清晰命名。
2. 在 `api/<域>.ts` 编写 `xxxApi`，只传 `url`、`method`、`data`，并带上请求/响应泛型。
3. 如需 mock，在 `api/mock.ts` 注册对应 `url + method` 分支。
4. 如需真实服务、特殊 `baseUrl`、关闭 mock 或定制 header，只修改 `utils/request.ts` 的统一配置，不改业务接口文件。

## 8. 状态管理（Pinia）

- 采用 **Options 写法**（`state` / `getters` / `actions`），与 `stores/user.ts`、`stores/workOrder.ts` 保持一致。
- `state` 必须带类型（独立 `interface XxxState`）。
- 需要持久化的状态通过 `utils/storage.ts` 读写，初始值从 storage 还原（参考 `useUserStore` 的 `token` / `userInfo`）。
- 异步 action 的标准范式：`loading` 防重入 + `try/catch/finally` + `error` 落库：

  ```ts
  async fetchList(reset = false) {
    if (this.loading) return
    this.loading = true
    this.error = ''
    try {
      const result = await getWorkOrderListApi({ ...this.queryParams })
      this.list = reset ? result.list : [...this.list, ...result.list]
    } catch (error) {
      this.error = error instanceof Error ? error.message : '加载失败'
    } finally {
      this.loading = false
    }
  }
  ```

## 9. 路由与权限

- 页面必须在 `pages.json` 的 `pages` 中注册；项目统一 `navigationStyle: "custom"`，顶部导航用自研 `AppNavbar` 组件。
- tabBar 五个主页面在 `pages.json` 配置，跳转 tab 页用 `uni.switchTab`，非 tab 页用 `uni.navigateTo` / `uni.redirectTo` / `uni.reLaunch`。
- 登录态拦截集中在 `utils/permission.ts`：
  - `setupPermission()` 在 `main.ts` 启动时注册全局路由拦截（`navigateTo` / `redirectTo` / `reLaunch` / `switchTab`）；
  - 新增需要登录保护的页面，要把路径加入 `protectedRoots`；免登录页加入 `whiteList`；
  - 未登录访问受保护页统一 `reLaunch` 回登录页。

---

## 10. 本地存储

- **一律通过 `utils/storage.ts` 封装读写**，禁止直接调用 `uni.setStorageSync` / `getStorageSync`。
- key 用模块顶部的大写常量（`CYC_SECURITY_*`），新增存储项先定义 key 常量再封装 `set/get/clear` 三件套。
- 读取返回值统一做空值兜底（`return value || null` / `|| ''`）。

## 11. 原生插件（App-plus）规范

AI 检测能力由 Android 原生插件 `AiDetectPlugin` 提供（`nativeplugins/AiDetectPlugin`），前端集成见 `pages/plugin-check/index.vue`。

- **条件编译**：所有原生相关代码用 `// #ifdef APP-PLUS ... // #endif` 包裹，H5 端必须降级可用（页面用 `isAppPlusRuntime` / `pluginStatus` 提示「不支持原生插件」）。

  ```ts
  // #ifdef APP-PLUS
  isAppPlusRuntime = true
  try {
    aiDetect = uni.requireNativePlugin('AiDetectPlugin') as AiDetectPlugin
  } catch (error) {
    console.error('获取 AiDetectPlugin 失败', error)
  }
  // #endif
  ```

- **调用前先校验**：通过 `checkPlugin()` 校验运行环境与方法存在性，再调用，失败给 `uni.showToast` 提示。
- **回调约定**：插件以 `callback(res)` 回传，按 `res.type`（`activity_opened` / `detect_result` / `snapshot` / `snapshot_error` / `error`）分发处理，`res.success === false` 视为失败分支。回调里收到的字段都要按可选类型声明（见 `DetectCallbackResult`）。
- **插件契约**：`startDetect(options, callback)` 的入参（`pipelineMode` / `detectInterval` / `targetModel` 等）与回调字段需与原生侧保持一致，模型路径等参数集中在 `targetModels` 常量，不要散落。
- **插件包结构**：`package.json`（`_dp_nativeplugin` 配置）+ `android/AiDetectPlugin-release.aar`；升级 AAR 时同步维护 `version` 与依赖声明。

## 12. 错误处理与用户提示

- 用户可见的错误统一用 `uni.showToast({ title, icon: 'none' })`，成功用 `icon: 'success'`。
- 捕获异常统一用 `error instanceof Error ? error.message : '兜底文案'` 取信息，避免直接抛 `[object Object]`。
- 网络/系统级异常给统一兜底文案（如「网络异常，请稍后重试」），业务级错误透传后端 `message`。
- 调试日志用 `console.log/warn/error`，关键节点保留（如插件回调），但不要在生产路径打印敏感信息。

## 13. Git 提交规范

遵循 Conventional Commits（与现有历史一致）：

```
<type>: <简明描述>

# 示例
feat: refine ai detection pipeline page
fix: adapt ai detection result display
```

常用 `type`：`feat`（新功能）、`fix`（修复）、`refactor`（重构）、`style`（样式）、`docs`（文档）、`chore`（杂项）。

**提交前自检：**

1. `npm run type-check` 通过；
2. 无新增 `any`/`console` 噪声、无注释掉的死代码；
3. 复用既有 `request` / `storage` / `permission` / 样式 token，未重复造轮子。

## 14. 新增功能落地清单（速查）

新增一个业务页面的标准步骤：

1. `types/<域>.ts` —— 定义 `Params` / `Result` / 实体类型；
2. `api/<域>.ts` —— 编写 `xxxApi`（带泛型，走 `request`）；必要时在 `api/mock.ts` 注册 Mock；
3. `stores/<域>.ts` —— 如需共享状态，建 Pinia store（Options 写法 + loading/error 范式）；
4. `pages/<域>/index.vue` —— `<script setup>` 编排 UI，复用 `AppNavbar` 与样式 token；
5. `pages.json` —— 注册页面（`navigationStyle: custom`），如需登录保护同步更新 `utils/permission.ts` 的 `protectedRoots`；
6. `npm run type-check` 通过后提交（Conventional Commits）。
